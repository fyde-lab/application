# CLAUDE.md

`fyde-application` is the Kotlin Multiplatform + Compose Multiplatform client (Android, iOS,
Desktop/JVM, Web JS + Wasm) on top of `../sdk`, reached through this repo's own UniFFI bindings
(`sdkBridge`, whose `rust/` crate wraps `fyde-sdk`).

## Rules

- **`App.kt` owns every `FydeSdk` call** and maps results into each screen's `*UiState`;
  screens stay presentation-only.
- **Never filter documents or compute filter choices in the app.** Search and filter chips go
  through `FydeSdk.searchDocuments`/`searchDocumentFacets` (see `VaultQuery.kt`); the chips
  only offer what the SDK's facets return. Grouping the SDK's results by month for display is fine.
- **Don't handle `SessionExpired` per screen.** Each platform's `sdkCall` reports
  `FfiException.SessionExpired` to `SessionExpiry` (`FydeSdkException.kt`); `App.kt` collects
  it and returns to `LoginScreen`. `App.kt` also polls `FydeSdk.isConnected` while signed in,
  since background sync can end the session without a failing call.
- **Bindings (`sdkBridge/rust/src/lib.rs`):** every exported `FydeClient` method runs through
  `FydeClient::localized`, so errors cross as `FfiError` worded in the user's language; never
  add a `From<Error> for FfiError`. `FfiError` is generated from the SDK's exported
  `fyde_sdk::for_each_error_code!`, and the `Ffi*` mirrors of SDK types must follow any SDK
  change (e.g. a new `ProgressStep` needs an `FfiProgressStep` variant). Keep its uniffi
  namespace `fyde_sdk` (Kotlin package `uniffi.fyde_sdk`).
- **Visual rules:** `design/design-system.md` is the source of truth (tokens in
  `shared/.../theme/`, components in `shared/.../components/`). Root `DESIGN.md` is superseded —
  don't implement against it.

## Commands

Load `shell.nix` first (`nix-shell` or direnv): it provides JDK 21 (`JAVA_HOME` is otherwise
unset), the Rust toolchain `sdkBridge` needs to build `../sdk`, and desktop's native libs.

```sh
./gradlew :androidApp:assembleDebug
./gradlew :desktopApp:run                    # :desktopApp:hotRun --auto for hot reload
./gradlew :webApp:wasmJsBrowserDevelopmentRun # or :webApp:jsBrowserDevelopmentRun
./gradlew :shared:jvmTest                     # also: testAndroidHostTest, wasmJsTest, jsTest, iosSimulatorArm64Test
```

- iOS: open `iosApp/iosApp.xcodeproj` in Xcode (builds `Shared.framework`); iOS targets only
  build on macOS hosts.
- Use the `run-fyde-application` skill to run/screenshot the desktop app headlessly.
- **Server URL is fixed at build time** (`BuildConfig.SERVER_URL`, generated by `shared`'s
  `generateBuildConfig`): dev builds → `http://127.0.0.1:40051`; release builds (any requested
  task naming `release`/`production`/`distribution`/`distributable` or starting with `package`,
  or Xcode Release) → `https://doc.halium.fr`. Override with `-Pfyde.serverUrl=<url>` (e.g.
  `http://10.0.2.2:40051` from the Android emulator). Abbreviated task names (`aR`) are not
  detected as release — spell them out.

## Architecture

- `shared/` — all app code and UI, standard KMP source sets (`commonMain`, `androidMain`,
  `iosMain`, `jvmMain`, `jsMain`, `wasmJsMain`, `webMain` + matching tests). Platform APIs use
  `expect`/`actual` (template: `Platform.kt`). Android namespace `com.peltoche.fyde.shared`.
- `sdkBridge/` — UniFFI bindings to `../sdk` (`ch.ubique.uniffi.plugin`), generated from
  `sdkBridge/rust/` (`fyde-sdk-bridge`): a `cdylib`/`staticlib` crate depending on `fyde-sdk`
  from the remote `master` of `github.com/fyde-lab/sdk` (not the local `../sdk` checkout;
  `Cargo.lock` pins the commit, `cargo update -p fyde-sdk` bumps it), holding `FydeClient` and the `Ffi*` mirror types. Test it with `cargo test` from
  `sdkBridge/rust/` (it dev-depends on the SDK's `testing` feature for `Fake*` fixtures).
  `FydeSdk.kt` is an `expect object` with per-platform `actual`s; Web is stubbed (`fyde-sdk`
  can't compile to wasm).
- `androidApp/`, `desktopApp/` (`com.peltoche.fyde.MainKt`), `webApp/`, `iosApp/` (Xcode, not
  Gradle) — thin shells bootstrapping `App()`; no business logic.

Screens (all in `shared/src/commonMain/kotlin/com/peltoche/fyde/`):

- Shell: `TopLevelScaffold.kt` hosts the Vault (Coffre), Sources (`TopLevelDestination.Scripts`), Settings — a top navigation bar
  at Expanded (`AppNavigationTopBar`, with Settings and the screen's `primaryAction` at its
  far end), a bottom bar below.
- Vault (Coffre): `VaultScreen.kt` (home V1/D6 and the shared pieces), `VaultCategoryPage.kt`
  (V3, D1, D2's list column), `VaultDocumentPage.kt` (V6, V7, D2's pass and preview), backed by
  `App.kt`'s `VaultContainer`, which holds the open page as a `VaultFocus` and reloads the home
  (category facets, each category's newest, latest arrivals) and the open category (facets
  without and with the subcategory, every page of results) on each changelog event. Below
  Expanded one page at a time; at Expanded D1's card grid, and an open document beside its
  category's list (D2). Device counts come from `listSessions`. What the SDK can't back
  (amounts, issuers, an "À classer" card, sharing, reclassifying) is left out.
- Sources: `SourcesTabScreen.kt` (the design's S1–S7, D4), backed by `App.kt`'s
  `SourcesTabContainer` (scrapers only; quota from `getUsage`). S1–S6 are pages at
  Compact/Medium; Expanded is D4, a table sortable by source and status beside a detail panel.
  Which page is open is a `SourceFocus` held by the container. Connect = install + enable, then
  `ScraperRuns.runOnceInstalled` with the values just installed (it waits until they've synced)
  and S4; editing credentials reinstalls, a blank secret keeping the installed one
  (`validatedCredentials`); remove only disables (no uninstall event yet). Statuses come from
  `ScraperRuns` (this app session's runs): no run history, schedule, counts or categories.
- Settings (`SettingsScreen.kt`, the design's Moi M1–M3 and M5–M8): a menu (seal card,
  Sécurité, Appareils, Offre et usage, Apparence et langue, logout) whose pages push inside the
  tab at Compact and open beside it at Medium/Expanded; which page is open is screen state.
  Pages: Sécurité and Ce que voit le serveur (static), `SessionsSection.kt` (M5, `listSessions`;
  revoke another device via `revokeSession` after confirmation, then re-fetch sessions and
  usage), `PlanUsageSection.kt` (M6, `FydeSdk.getUsage`, re-fetched each time Settings opens),
  appearance and language (M7; the light/dark `theme/AppAppearance.kt` is held in `App()` above
  `AppTheme`, not persisted yet; no theme picker while `AppThemeOption` has one entry). Logout
  (M8, confirmed in an `AppDialog` that stays busy until it's done) is the only way to end this
  device's session and clears local state.
- `WelcomeScreen` (O1 at Compact, DO1 at Medium/Expanded): the first screen without a session,
  and after logout; leads to `RegisterScreen` or `LoginScreen` (an expired session goes straight
  to `LoginScreen`). DO1 splits the window with `SignInSplitLayout` (`SignInBrandPanel`, an
  `AuthBrandBand` at Medium), shared with the other desktop sign-in screens, beside a centred
  form naming the build's server.
- `LoginScreen` (O2 at Compact, DO2 at Medium/Expanded in `SignInSplitLayout`; after a failure,
  DO2c empties and refocuses the password): back to `WelcomeScreen`. `App.kt` passes why the
  session ended as `noticeMessage` (warning note, `sessionNotice`), separate from a failed attempt's
  `errorMessage` (error note, `authError`).
- `RegisterScreen` (the original form at Compact, DO3 at Medium/Expanded in
  `VaultCreationSplitLayout`; DO3b's mismatch error shows on blur or submit): back to
  `WelcomeScreen`; on success, `RecoveryKitScreen`. DO3 requires ticking the key-warning acknowledgement; its strength meter
  (`passwordStrength`, by length) only advises — the server sets no password rule.
- `RecoveryKitScreen` (O6 at Compact, DO6 at Medium/Expanded): the vault-creation step after
  the account. `App.kt` calls `FydeSdk.generateRecoveryKey` as it opens (each call replaces the
  account's key, so only once per visit, plus Retry) and keeps the 24 words only while it's open.
  Save the PDF (`recoveryKitPdf`, a hand-written one-page PDF, through `rememberDocumentSaver`)
  everywhere; Print (`rememberPdfPrinter`) on desktop (PDFBox) and Android (`PrintManager`) only;
  Android keeps the screen out of screenshots (`ScreenshotGuard`, `FLAG_SECURE`). Both "I've put
  it somewhere safe" and "Later" lead on to `SourcesScreen`, keeping the key. `VaultCreationStep` drives
  `VaultCreationBrandPanel`'s stepper and the phone's `VaultStepDots`: list only steps that have
  screens (notifications doesn't yet).
- `SourcesScreen` (O7/O7b at Compact, DO7/DO7h at Medium/Expanded in `VaultCreationSplitLayout`):
  the public scrapers (`listPublicScripts`, `SCRAPER` only) to tick, searched with
  `filterScripts`. `App.kt` holds the selection (in ticking order) and the plan counter
  (`AppPlanQuota`, from `getUsage` via `sourceQuotaOf`; hidden without a limit or if `getUsage`
  fails): at the limit unticked sources dim and can't be ticked. On desktop the cards scroll inside a
  fixed-height grid so the connect button stays under them. No back button (it would
  regenerate the recovery key) and no category chips (scripts have no category yet). Passer →
  Vault; Connecter → `ConnectSourceScreen`, keeping the ticks for its back button.
- `ConnectSourceScreen` (S3 inside onboarding at Compact, DO7b at Medium/Expanded in
  `VaultCreationSplitLayout`, whose brand panel lists the ticked sources as `VaultSource`s):
  each ticked source in turn, `App.kt` holding the queue (`connectQueue`/`connectIndex`). One
  field per script parameter (`ScriptParameterField`, `ScriptParameters.kt`, shared with the Sources tab);
  Connecter installs and enables it, then `ScraperRuns.runOnceInstalled` queues its first run
  until the installation has synced to this device, and opens `SourceFetchingScreen`. Passer
  cette source / back move along the queue; after the last source → Vault until DO7d–DO7g
  and DO8 exist. No "Récupérer automatiquement" switch: fyde-sdk has no scheduled runs.
- `SourceFetchingScreen` (DO7c at Medium/Expanded, a stacked version at Compact): the connected
  source's first run as a `RunStepper` (Connexion → Recherche → Téléchargement i / n →
  Rangement), from `ScraperRuns`' typed `stepKind`/`update`/`found` and, once over, its
  `outcomes` entry (`sourceFetchStatusOf` in `App.kt`). Source suivante / Continuer moves on
  without stopping the run; Attendre ici moves on by itself once it succeeds; a failure shows
  the SDK's message with Réessayer. No step times or duration estimate (nothing records them).
- `InsecureStorageSheet` (O4 on phones, DO4b on desktop — `Platform.isDesktop` picks the
  wording and the desktop's Retry): over `LoginScreen`/`RegisterScreen` when the device has no
  OS credential store (`FydeSdk.isSecureStorageAvailable`, checked as each form opens and again
  after a failed attempt). Submitting opens it; once the user accepts, `App.kt` reruns the
  attempt with `allowInsecureStorage` (fyde-sdk refuses with `SecureStorageUnavailable`
  otherwise); Retry re-checks and, if a keyring answers now, runs it without. The screens
  themselves know nothing of it.
- `LoginScreen`, `RegisterScreen`, `SessionLimitScreen`: when `FydeSdk.login` returns
  `FydeLoginOutcome.SessionLimitReached`, `App.kt` shows the account's sessions, keeps the typed
  credentials in `Screen.SessionLimit` only while it's open, and re-runs login with the picked
  session as `replaceSessionId` (the server's login exchange is single-use). `SessionLimitScreen`
  is O5 at Compact and DO5 at Medium/Expanded (in `SignInSplitLayout`): a radio group of the
  sessions, a phone or laptop glyph guessed from the session's device name. Its "See plans"
  shows only given `onSeePlans`, which `App.kt` doesn't pass yet (no plans page before sign-in).

Toolchain versions are pinned in `gradle/libs.versions.toml` (Kotlin 2.4.20, Compose MP 1.12.0,
AGP 9.1.1); JDK 21 via Foojay (`gradle/gradle-daemon-jvm.properties`).
