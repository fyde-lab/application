# CLAUDE.md

`fyde-application` is the Kotlin Multiplatform + Compose Multiplatform client (Android, iOS,
Desktop/JVM, Web JS + Wasm) on top of `../sdk`, reached through this repo's own UniFFI bindings
(`sdkBridge`, whose `rust/` crate wraps `fyde-sdk`).

## Rules

- **`App.kt` owns every `FydeSdk` call** and maps results into each screen's `*UiState`;
  screens stay presentation-only.
- **Never filter documents or compute filter choices in the app.** Search and filter chips go
  through `FydeSdk.searchDocuments`/`searchDocumentFacets` (see `VaultQuery.kt`); the chips
  only offer what the SDK's facets return. Grouping the SDK's results by month for display is fine.
- **Don't handle `SessionExpired` per screen.** Each platform's `sdkCall` reports
  `FfiException.SessionExpired` to `SessionExpiry` (`FydeSdkException.kt`); `App.kt` collects
  it and returns to `LoginScreen`. `App.kt` also polls `FydeSdk.isConnected` while signed in,
  since background sync can end the session without a failing call.
- **Bindings (`sdkBridge/rust/src/lib.rs`):** every exported `FydeClient` method runs through
  `FydeClient::localized`, so errors cross as `FfiError` worded in the user's language; never
  add a `From<Error> for FfiError`. `FfiError` is generated from the SDK's exported
  `fyde_sdk::for_each_error_code!`, and the `Ffi*` mirrors of SDK types must follow any SDK
  change (e.g. a new `ProgressStep` needs an `FfiProgressStep` variant). Keep its uniffi
  namespace `fyde_sdk` (Kotlin package `uniffi.fyde_sdk`).
- **`fyde.browser`'s webview** (`sdkBridge/rust/src/browser.rs`): `FydeClient.init`'s
  `browserEngine`, a `WebviewEngine` callback interface the app implements on Android and iOS;
  `null` on desktop, where the bindings run `fyde-browser-wry` themselves (a desktop-only
  dependency, so mobile builds never pull in tao/wry/GTK). Without one on mobile, `fyde.browser`
  fails with `BrowserFailed`. An engine only hosts webviews (one isolated, ephemeral data store
  per session, or it refuses to open one): every decision is the SDK's, asked of the
  session's `FfiWebviewHandler`. Never put a rule in an engine. iOS's is `IosWebviewEngine`
  (iosMain): a WKWebView per run on its own non-persistent `WKWebsiteDataStore`, in the key
  window (1×1 and nearly transparent unless visible); calls hop to the main queue and wait.
  Android's is `AndroidWebviewEngine` (androidMain): a WebView per run on its own androidx.webkit
  profile, deleted with it (leftovers at the next start); without multi-profile support (WebView
  < 110) it refuses to open one. Its WebView sits in `ResumedActivity`'s window (1×1 and
  transparent unless visible); calls hop to the main thread and wait. `CookieManager` only gives
  names and values, so cookies read back lose their other attributes.
- **The system back gesture does what the visible back control does.** `AppBackButton`,
  `AppPageBar` and `AppTopBar`'s `onBack` register a `SystemBackHandler` (Android's system
  back, iOS's edge swipe; off on desktop and web, where Compose maps Esc to back). A page that
  goes back through another control (an Annuler, a close button) calls `SystemBackHandler`
  itself; design-system samples pass `handlesSystemBack = false`.
- **Visual rules** (`design/README.md`): `design/current/` is the app as built
  (`design-system.md` read from the code, screens rendered from it in English), the base new UI
  starts from; new or changed UI follows its accepted proposal in `design/proposals/NNN-*/`.
  Tokens live in `shared/.../theme/` (mirrored by `design/kit/tokens.css`), components in
  `shared/.../components/`, glyphs in `shared/.../icons/`. A UI change updates `current/` in the
  same PR: a `shot(...)` in `ScreenshotFixtures.kt` for a new screen or state, `design/capture.sh`
  to re-render, `current/design-system.md` by hand. Never edit `current/` otherwise, nor another
  proposal's folder. Root `DESIGN.md` and `design/proposals/000-original-design/` (the earlier
  target design) are history: don't implement against them.

## Commands

Load `shell.nix` first (`nix-shell` or direnv): it provides JDK 21 (`JAVA_HOME` is otherwise
unset), the Rust toolchain `sdkBridge` needs to build `../sdk`, and desktop's native libs.

```sh
./gradlew :androidApp:assembleDebug
./gradlew :desktopApp:run                    # :desktopApp:hotRun --auto for hot reload
./gradlew :webApp:wasmJsBrowserDevelopmentRun # or :webApp:jsBrowserDevelopmentRun
./gradlew :shared:jvmTest                     # also: testAndroidHostTest, wasmJsTest, jsTest, iosSimulatorArm64Test
```

- iOS: open `iosApp/iosApp.xcodeproj` in Xcode (builds `Shared.framework`); iOS targets only
  build on macOS hosts.
- Use the `run-fyde-application` skill to run/screenshot the desktop app headlessly.
- **Server URL is fixed at build time** (`BuildConfig.SERVER_URL`, generated by `shared`'s
  `generateBuildConfig`): dev builds → `http://127.0.0.1:40051`; release builds (any requested
  task naming `release`/`production`/`distribution`/`distributable` or starting with `package`,
  or Xcode Release) → `https://doc.halium.fr`. Override with `-Pfyde.serverUrl=<url>` (e.g.
  `http://10.0.2.2:40051` from the Android emulator). Abbreviated task names (`aR`) are not
  detected as release — spell them out.

## Architecture

- `shared/` — all app code and UI, standard KMP source sets (`commonMain`, `androidMain`,
  `iosMain`, `jvmMain`, `jsMain`, `wasmJsMain`, `webMain` + matching tests). Platform APIs use
  `expect`/`actual` (template: `Platform.kt`). Android namespace `com.peltoche.fyde.shared`.
- `sdkBridge/` — UniFFI bindings to `../sdk` (`ch.ubique.uniffi.plugin`), generated from
  `sdkBridge/rust/` (`fyde-sdk-bridge`): a `cdylib`/`staticlib` crate depending on `fyde-sdk`
  from the remote `master` of `github.com/fyde-lab/sdk` (not the local `../sdk` checkout;
  `Cargo.lock` pins the commit, `cargo update -p fyde-sdk` bumps it), holding `FydeClient` and the `Ffi*` mirror types. Test it with `cargo test` from
  `sdkBridge/rust/` (it dev-depends on the SDK's `testing` feature for `Fake*` fixtures).
  `FydeSdk.kt` is an `expect object` with per-platform `actual`s; Web is stubbed (`fyde-sdk`
  can't compile to wasm).
  On Android, `AppContextInitializer` also calls `PlatformVerifier.initialize` (JNI, exported by
  `sdkBridge/rust/src/android.rs`): the SDK's HTTPS clients check certificates through
  `rustls-platform-verifier`, which panics on first use without the app context. Its Kotlin half
  (`org.rustls:rustls-platform-verifier`, from its GitHub Maven repo in `settings.gradle.kts`) is
  pinned by `sdkBridge/build.gradle.kts` to `rustls-platform-verifier-android`'s version in
  `rust/Cargo.lock`, and kept from R8 by `androidApp/proguard-rules.pro`.
- `androidApp/`, `desktopApp/` (`com.peltoche.fyde.MainKt`), `webApp/`, `iosApp/` (Xcode, not
  Gradle) — thin shells bootstrapping `App()`; no business logic.

Screens (all in `shared/src/commonMain/kotlin/com/peltoche/fyde/`):

- Shell: `TopLevelScaffold.kt` hosts the Vault (Coffre), Sources, Settings — a bottom bar at
  Compact, T2's 80dp icon rail at Medium and the 260dp sidebar at Expanded (D6/T1), both in
  `AppSidebar.kt`: Whole vault, À classer (while it holds documents), DOSSIERS with its "+"
  (`TopLevelNavigation.onNewFolder`: D10 for a top-level folder over the open vault page, or
  over the vault's home from another destination; Expanded only), the folder tree (top-level
  folders by name, the open folder's branch expanded; the rail shows top-level folders only),
  Sources, the seal line, Settings. `App.kt` holds its figures: the folders (`listFolders`) and
  document counts from the facets, reloaded on each changelog event; source and device counts (`getUsage`, `listSessions`) as each destination
  opens and after this device changes them. The content beside it gets the size class of the
  window's width minus the sidebar, never below Medium. One layout tree at every size, so
  crossing a breakpoint keeps the content's state. Size classes are computed from
  `LocalWindowInfo`, never measured with `BoxWithConstraints`: a class change during layout
  disposes open popups mid-pass and crashes the desktop renderer.
- Vault (Coffre): browsed by the user's folders. `VaultFolders.kt` indexes `listFolders` (by id,
  each level by name ignoring case and accents, a folder's path; a subfolder shows its top-level
  folder's appearance, mapped onto the `AppColors.category` palette) and is provided to rows,
  cards and passes as `LocalVaultFolders`. `VaultScreen.kt` (home V1/D6 and the shared pieces),
  `VaultFolderPage.kt` (V3, D1, D2's list column), `VaultSearchPage.kt` (V4, V5),
  `VaultDocumentPage.kt` (V6, V7, D2's pass and preview), backed by `App.kt`'s `VaultContainer`,
  which holds the open page as a `VaultFocus` and reloads the folders, then the home (À classer
  while it holds documents, every top-level folder with its count and newest, latest arrivals),
  the open folder (its subfolders' counts from the vault-wide facets, year chips, every page of
  results) and the open search (`VaultQuery`, debounced while typing, RELEVANCE order) on each
  changelog event; a folder deleted meanwhile closes its page. A folder page lists every document
  below it (the SDK's `FolderFilter::Within` includes subfolders), not only its own. Below
  Expanded one page at a time; at Expanded D1's card grid, and an open document beside its
  folder's list or the search's results (D2). A folder page's search starts within it. Device counts come from `listSessions`. A document's
  pass template, its Informations rows and its rows' issuer and amount come from its attributes
  (`FydeDocument.attributes`): the rules are pure functions in `DocumentAttributes.kt` (tested in
  `DocumentAttributesTest`), their wording in `DocumentAttributesText.kt`. What the SDK can't back
  (sharing, recent searches, the Source facet) is left out.
  First pages (`DocumentThumbnails.kt`): document rows, D1's cards and V6's file row show a
  PDF's first page only as stored in the SDK's SQLite database (`FydeSdk.documentThumbnail`, one
  fixed-size PNG per document, `THUMBNAIL_SIDE`, 512 px a side, so every box scales that one
  image). Nothing draws one on request and the app caches none in memory: each box reads it back
  through `LocalDocumentThumbnails`. Only the SDK's background job draws them
  (`FfiBackgroundJobs.thumbnails`). Both follow `FydeSdk.showsThumbnails` (desktop, Android and
  iOS; Web has no SDK): where it's off the job never starts and `LocalDocumentThumbnails` is
  `null`, so no thumbnail is ever drawn or asked for. Other kinds, and a document with no stored page, keep the folder's tile.
  Folder sheets (`VaultFolderSheets.kt`, a `FolderSheetState` in `VaultUiState.Loaded`, called
  back through `FolderCallbacks`): V12/D10 new folder (the home's "+ Nouveau dossier", a folder
  page's "+ Nouveau" and its actions' Nouveau sous-dossier), V13/D7 actions from a folder page's
  "…", editing the name and (top level only) colour and icon, V14/D8 moving through
  `FolderPicker` (browsable by level, the moved folder and what's below it left out, the current
  parent tagged Actuel), V15/D9 deleting (Les garder / Les supprimer aussi). Folders have no
  description (design-system.md § Folders' Filing). Each only publishes its event, busy until
  it's sent; the SDK's refusal (a taken name...) stays in the sheet. Deleting the open folder opens its parent.
  At Expanded, `VaultShortcuts` handles the keyboard on the open document, else the open folder:
  ⇧⌘N new folder (a subfolder of the open one), F2 rename (folders only: the SDK can't rename
  documents), ⇧⌘M move (V9 / D8), ⌘⌫ or Delete delete (D2c / D9); Ctrl for ⌘ off macOS.
  Drag and drop at Expanded (`VaultDrag.kt`, in-app rather than the platform's, provided as
  `LocalVaultDrag` by `VaultScreen`): document rows and cards and folder cards are
  `vaultDragSource`s, folder cards and sidebar rows `vaultDropTarget`s outlined while they'd take
  the item; never where it already is, a folder never into itself or below it, À classer takes
  documents only. A drop publishes through `FolderCallbacks.onDropDocument`/`onDropFolder`, its
  outcome a snackbar.
  Moving a document (V9, `MoveDocumentSheet`, a `DocumentMove` in `VaultUiState.Loaded`): from
  V8's Déplacer, D2's Déplacer button and "…"/right-click menu, and the filing card under the
  pass ("Rangé dans <path>" · Modifier, or "Dans À classer" · Ranger; no C'est bon, nothing
  records it). The picker opens on the document's folder's level, its folder tagged Actuel;
  `FydeSdk.moveDocument` only publishes, the document shows its new folder once synced.
  Deleting (V8's sheet, D2b's "…" menu and right-click, ⌘⌫ / Suppr, then V10 / D2c as a
  `DocumentDeletion` in `VaultUiState.Loaded`) calls `FydeSdk.deleteDocument`, which only
  publishes the event: the document leaves the lists once sync consumes it. On success the
  document closes with a snackbar; on failure the dialog keeps the SDK's wording in its note.
  Similar documents (`VaultSimilarPage.kt`, design-system.md § Similar documents, § Selection):
  `FydeSdk.similarDocuments` (the SDK's `similar` at its `DEFAULT_SIMILAR_MIN_CONFIDENCE`),
  shown as `similarityPercent` of its 0–1 confidence, never re-ranked or filtered here. A
  document's page (V6c, D2) ends with the three closest (`documentSimilar`, hidden while loading,
  when empty or when the SDK fails) and Tout voir, opening `VaultPage.Similar` (V16; D11 at
  Expanded, in D2's list column with the document kept open beside): the document it started
  from tagged Ce document, then up to 50 with checkboxes; the ticks live in the page
  (`VaultPage.Similar.ticked`). The `SelectionBar`'s Déplacer / Supprimer open V9 / V10 for
  several (`DocumentMove` and `DocumentDeletion` hold a list): `App.kt`'s `publishEach` sends one
  event per document in turn (the SDK has no batch call), going on past a refusal, and the
  sheet stays open on those refused. The starting document's row isn't refreshed after a
  move (the SDK has no metadata-only getter).
- Sources: `SourcesTabScreen.kt` (the design's S1–S7, S3b, S5c, S7b, D4), backed by `App.kt`'s
  `SourcesTabContainer` (scrapers only; quota from `getUsage`). A source can have several
  accounts (design-system.md § Accounts of a source): each is a `SourceAccount`
  (`SourceAccounts.kt`, one `FydeInstallation` of a script, its own installation id, label,
  credentials, runs and status), and every row, page, run and status is per account, keyed by
  installation id; the label shows ("Ameli · Marie") only once a source has several. The
  container re-reads `FydeSdk.listInstallations` on every changelog event. S1–S6 are pages at
  Compact/Medium; Expanded is D4, a table sortable by source and status beside a detail panel.
  Which page is open is a `SourceFocus` held by the container (`Connect` by script id, the
  others by installation id). Connect = install (a new installation) + enable, then
  `ScraperRuns.runOnceInstalled` with the values just installed (it waits until they've synced)
  and S4; Ajouter un autre compte (S5/S5c/D4) and S2's Autre compte open the same form for one
  more account (S3b, with Nom du compte; the plan counts sources, so it's never dimmed at the
  limit). Editing credentials reinstalls the same installation, a blank secret keeping the
  installed one (`validatedCredentials`) and its folder. Each account files into a folder
  (design-system.md § A source's folder, `SourceFolders.kt`): the connect form's Ranger dans
  row (`SourceFolderField`; Rangement automatique by default, S3b starting from the source's

  S5/S5c's and D4's Réglages row open S9/D12, `FolderPicker` with Rangement automatique as its
  top entry, whose Nouveau dossier ici (or Créer un dossier) opens the new-folder sheet named
  after the source; the folder it creates is picked at once. Changing it from S5/D4 reinstalls
  the account with its parameters, label and the new folder (no snackbar unless it fails). An
  install with a folder not synced yet waits for it (`awaitFolderSynced`: the SDK refuses a
  folder it doesn't know), and a folder no longer in `listFolders` reads Rangement automatique.
  The container's folders come from `listFolders`, re-read on every changelog event, plus those
  created here until they sync. Remove uninstalls the account (`FydeSdk.uninstallScript`,
  S7, or S7b for one among several) and disables the source with its last account. Statuses come from
  `ScraperRuns` (this app session's runs), else from each account's last report on this device
  (`FydeSdk.lastScriptRuns`, the SDK's `last_runs`, re-read as the tab opens and on each
  changelog event; `sourceStatusOfReport`: a run cut short by the app closing reads as stopped,
  "Interrompue"): no run history, schedule or categories.
  Arrêter (`ScraperRuns.stop`, `FydeSdk.stopScriptRun`) sits under S4's primary and in S5/D4's
  Lancer slot while the account runs, busy until the run has ended; a stopped run's outcome is
  `ScraperRunOutcome.Stopped` (from `FydeSdkException.isRunStopped`), shown muted, never as a
  failure (S4b's note, a snackbar with Relancer). The question dialog's dismiss stops the run.
